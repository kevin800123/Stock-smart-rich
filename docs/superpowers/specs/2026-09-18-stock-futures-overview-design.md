#### 失敗長得像成功（本設計最重要的一條）

| 情況 | HTTP | Content-Type | 大小 | 內容 |
|---|---|---|---|---|
| 正常 | 200 | `text/html;charset=MS950` | 150 KB | CSV |
| 區間超過一個月 | 200 | `text/html;charset=`**`UTF-8`** | 616 B | **HTML 警告頁** |
| 非交易日 | 200 | `charset=MS950` | **197 B** | **只有表頭** |

既有的 `taifex._post_csv` 只驗 `status_code == 200 and r.content`，**三種都會通過**，
而 HTML 警告頁還會被當成 MS950 解碼成亂碼。新抓取器必須另外驗三件事：

1. Content-Type 含 `charset=MS950`（擋掉 UTF-8 警告頁）
2. 第一行等於預期表頭（擋掉改版）
3. 該日「一般、非價差」列數落在合理區間（至少 1,200；正常 1,629）——擋掉表頭空檔

不動 `_post_csv` 本身（`fetch_chips_for_date` 等既有路徑依賴它），新寫一支專用的。

## 2. 計算規則

### 2.1 母合約（root）與熱門排序

- `root` ＝ 合約代碼前 2 碼。正常合約 ＝ `root+F`、調整後 ＝ `root+1`，兩者自動歸同一個 root。
  實測 09-17：340 個合約代碼收斂成 **320 個 root**，恰好 ＝ 320 正常 ＋ 20 調整後合併掉 20 個。
- **官方 STFTop10 口徑**：依 root 加總**所有非價差列、跨全部月份、跨一般與盤後**的成交量。
  實測 09-17 前五：CC 聯電、**QF 小型台積電**、CH 友達、FZ 華邦電、DQ 群創。
- 標準（CD）與小型（QF）是**不同 root**，所以「官方口數」天生就讓兩者各自成列，
  不需要額外處理。副標須註明「口數含小型合約，規模不同」。

#### 調整後合約只併成交量，絕不併價格

調整後合約（`CM1`）與正常合約（`CMF`）同 root、同月份，**但乘數是非標準的**
（實測 2020、2262、5965.5892、298.2795、110…）。若「取 root 內成交量最大的列」取到
調整後那一列，再套上標準的 2,000 乘數，算出來的保證金與契約價值**全是錯的，而且看不出來**。

所以：**root 合併只用於成交量加總**（官方口徑本來就這樣）；
**價格、漲跌%、結算價、期現價差、保證金一律只取代碼結尾為 `F` 的正常合約列**。
每個有調整後合約的 root 必定也有對應的 `F` 合約（320 root 全數成立），所以不會有洞。

### 2.2 主力月

**正常合約（`root+F`）的**「一般、非價差」列中**成交量最大**的月份，
**排除結算價為 0 的到期腳**（結算日當天到期腳仍在交易且可能量最大，但它的結算價是 0、
價差也收斂到 0）。全部無成交時取最小月份。

沿用 `parse_tx_history_csv` 既有的「取量最大」慣例（`parse_tx_quote_csv` 用的是「取最小月」，
本專案本來就有兩種寫法，這裡明確選前者並寫進註解）。

**沒成交不等於沒價格**：實測 09-17 的 1,629 列非價差一般列裡有 1,014 列當天無成交
（收盤欄是 `-`），但**全部 1,629 列都有結算價**（例：VQF 202611 收盤 `-`、結算 64.7），
320 個 root 沒有任何一個缺結算價。所以保證金全表可以涵蓋全部 320 檔，
冷門股期不會出現空白列——但它的「收盤／漲跌%」要顯示 `—` 而不是拿結算價冒充成交價。

**換月與到期的已知現象（不是錯誤，但要標）**：主力月換月那天，漲跌% 用官方欄位所以不會
跳空（參考價是同月份的前日結算），但**期現價差會跳一階**（換到遠月，持有成本較高）。
到期前幾天，到期月的價差自然收斂到接近 0。兩者都在 tooltip 標出主力月，讀者才知道在看哪一個月。

### 2.3 漲跌%

**直接用該列自己的「漲跌%」欄，不要自己算收盤對收盤。**
官方的參考價是**前一日結算價**不是收盤價：實測 CCF 202610 於 09-04 收 131、漲跌 6
→ 參考價 125.0 ＝ 09-03 結算價，而 09-03 收盤是 125.5。自己算會得 4.38% 對上官方 4.80%。
用官方欄位也順便避開「主力月換月」造成的假跳空。

### 2.4 期現價差（ticks）

`基差 = 期貨主力月結算價 − 現貨收盤價`，換算成 tick 數。

**股期的 tick 表與現貨不同**（2026-07-06 起）：
`<10:0.01 / 10–50:0.05 / 50–100:0.1 / 100–500:0.5 / 500–2500:1 / >=2500:5`；
ETF 期貨 `<50:0.01 / >=50:0.05`。現貨在 1000–2500 跳 5，**期貨跳 1**。

**必須沿著網格走，不可除以單一 tick**：實測 KBF 聯茂 S=495／F=501，
走網格得 **11** ticks，除 tick(F)=1 得 6，除 tick(S)=0.5 得 12。

現貨收盤取既有的 `_quotes_for` / `_otc_quotes_for`（MI_INDEX ALL／TPEx dailyQuotes，
本來就逐日快取、且含 ETF）。**不用 `stock_ohlc`**：它濾掉 ETF 且很稀疏。

誠實標註（**這條不可省**）：期貨結算價是 13:44–13:45 的成交量加權均價、現貨收盤是
13:30 的集合競價，**兩者時間不同步**，實測光是「用結算價還是用收盤價」就會差最多 5 ticks。
標題寫「收盤價差（期貨 13:45 結算 vs 現貨 13:30 收盤，時間不同步）」。

排除：調整後 `X1` 合約（乘數非標準）、14 檔交易到 16:15 的 ETF 期貨（另標）。
標準與小型共用同一個結算價，所以**同一檔標的只列一列**。

### 2.5 保證金

```
單口原始保證金 = ROUND_HALF_UP(期貨價格 × 契約乘數 × 原始保證金適用比例)   # 整數元
N 口          = 單口 × N                                              # 先四捨五入再乘
```

四條紀律，每一條都有實測依據：

1. **必須用 `Decimal` ＋ `ROUND_HALF_UP`，不可用 Python 的 `round()`**。
   實測 1,181 個（合約, 月份）裡有 **101 個**兩者結果不同。
   券商實際數字驗得出來的兩個半元案例：南亞 CAF 96,592.5 → **96,593**、
   小型緯穎 PWF 42,808.5 → **42,809**（`round()` 各少 1 元）。
2. **直接用官方公布的兩位小數比例欄，不要用「結算比例 × 1.35 ／ × 1.035」反推**。
   維持保證金兩種算法在 1,181 個合約月中有 **467 個**結果不同，
   券商 20 筆對照表對得上的是**公布欄位**（例如 15.53%，不是 15.525%）。
3. **ETF 期貨不套公式**，用公布的固定金額（標準為 1,000 的倍數、小型恰為標準的 1/10）。
4. **微台 TMF 是固定 35,050**（維持 26,900），官方明文 TMF ＝ TX/20、MTX ＝ TX/4。

**價格輸入的誠實說法**：官方 `margingReqSSF` 只對**盤後時段**明文規定「採前一一般交易
時段每日結算價」，日盤沒有規定，券商實際是用**最新成交價**算（實測 20/20 對得上，
其中 8 筆收盤不等於結算）。本站用「當日結算價」是可重現、可標日期的選擇，但畫面上必須寫
**「以 YYYY-MM-DD 結算價估算，實際以期貨商收取為準」**——這是估算，不是券商會收的那個數字。

驗算樣例（寫進測試）：

- CDF 202610，09-17 結算 2,432 → 2,432 × 2,000 × 13.50% ＝ **656,640**
- QFF 202612，09-17 結算 2,453 → 2,453 × 100 × 13.50% ＝ 33,115.5 → **33,116**
- DHF 202610，251.5 × 2,000 × 16.20% ＝ **81,486**
- NYF（0050）＝ 87,000（固定）、SRF ＝ 8,700
- TMF × 2 ＝ **70,100**

### 3.3 排程

`job_schedule` 新增一筆（現有時段已占 17:00／17:30／18:30／19:30／21:00／21:10／21:30／21:40）：

```python
{"id": "ssf_daily", "family": "ssf_daily",
 "hour": "17,18,20", "minute": "15", "dow": "mon-fri"}
```

每次執行（走既有 `run_job`，所以自動有去重、`job_runs` 紀錄與啟動補跑）：

1. 週末略過
2. 保證金表重抓（獨立 try/except——它與行情無關，行情沒到齊也要更新）
3. 今天已存且列數合理 → `skipped: already_done`
4. 抓 D，過三道守衛才寫；另**重抓前 2 個交易日**（官方偶有更正）
5. 刪 60 個交易日以前的列

**沒有量到 D 的 CSV 幾點才有**（逐筆 zip 的 Last-Modified 是 16:38，據此推測 17:15 多半有了）。
17:15 抓不到就 18:15、20:15 再試，這正是三個時段的用意。

回補：`GET /api/ssf/backfill?days=30`，一次一個不超過一個月的區間（沿用 `chips/backfill`
「重複呼叫直到 remaining 不再下降」的既有契約）。

**Zeabur 可達性**：production 本來就每天 POST `www.taifex.com.tw`（`fetch_chips_for_date`），
所以主機本身通。**沒測過的是** `specialid/all` 這個表單、`stockLists`、`stockMarginingDown`。
第一次部署後先打 `/api/ssf/backfill?days=1` 確認；若打不動，退回本專案已有兩次先例的
「本機抓→匯入」（`scripts/sync_ohlc.py`、`sync_report_financials.py`）。

### 3.4 API

- `GET /api/ssf/overview?date=` — 一次回四個區塊要的全部資料 ＋ `coverage`（資料日、

- `GET /api/ssf/margin` — 全部合約的**單口**原始／維持保證金、比例、乘數、三個更新日期。

4. **近 10 交易日排行熱力圖**：10 列（名次 1–10）× 10 欄（交易日），
   格子 ＝ 簡稱 ＋ 當日漲跌%。**白字疊在色塊上 → 必須用 `--up-fill`/`--down-fill`**，
   `sectorColor` 加一個 `scale` 參數（預設仍 3%，這裡用 7%），不改既有呼叫端。
   缺的交易日是**空欄**，絕不拿別天的資料頂替。
5. **原始保證金試算**：可搜尋排序的全表（320 檔股期 ＋ ETF 期貨 ＋ 台指／小台／微台），
   欄位：標的｜契約乘數｜原始比例｜**1 口原始保證金**｜維持保證金｜**N 口合計**。
   上方一個「口數」輸入框（`input`，委派在容器上——CSP 禁 inline handler）。
   金額**不著紅綠**。頂端一行標「以 YYYY-MM-DD 結算價估算；比例更新日 YYYY/MM/DD；
   實際以期貨商收取為準」。

6. **未平倉增減榜**（追加）：`當日 OI − 前一交易日 OI`，增加最多／減少最多各 10 檔。
   資料零成本（OI 本來就在同一份 CSV 裡），而且**它比成交量更能分辨「有人在建倉」還是
   「只是當沖來回」**——大量搭配 OI 大增是建倉，大量搭配 OI 大減是平倉出場。
   前一日缺列就整檔不列（同「餘額 0 與沒抓到是兩件事」的既有紀律），不當成 0。
   OI 增減**不是漲跌方向**，所以**不著紅綠**，用中性色＋箭頭。

### 4.6 個股頁順帶顯示保證金（追加）

查 2330 時，個股頁的基本面區塊多一行：
「台積電期 1 口 656,640　小型台積電期 33,116（以 2026-09-17 結算價估算）」。

全表回答「哪一檔門檻低」，個股頁回答「我正在看的這檔要多少」——**兩個不同的問題、
兩個入口，共用同一份 `GET /api/ssf/margin` 資料**。沒有股期的個股就整行不出現
（`#stock-ssf-margin:empty { display:none }`，同 `#today-focus` 的既有做法）。

前端成本很低：`/api/ssf/margin` 已經回全表，個股頁只要用 `股票代號 → [合約]` 反查一個 key。
**反查索引在後端組**（端點多回一個 `by_stock` 對照），不要讓 `app.js` 自己掃 320 列組 map——
那是同一份資料的第二種形狀，放前端會跟熱力圖那組一樣各自漂移。

### 4.7 自算選股加「有股期」欄（追加）

## 8. 第 0 步：production 可達性探測（先做，使用者拍板）

整份設計目前押在一個**沒有驗證過的假設**上：這些端點從 Zeabur 打得到。
本專案已經被這件事咬過三次（Yahoo 被 IP 封、mopsfin `/compare/report` 打不動、
`/api/ohlc/backfill` 連續熔斷），每一次都是**寫完才發現**、然後整條路要改成「本機抓→匯入」。
所以先花一次部署確認，比寫完再退場便宜得多。

臨時端點 `GET /api/ssf/probe`（沿用已移除的 `net-check`／`tv-check` 先例，**驗完就拆**）：

- **目標網址全部寫死在程式裡，不吃任何使用者輸入**——不做成通用取回器，否則就是一個 SSRF。
- 逐項回報 `ok / http / content_type / bytes / elapsed / head`，任何一項失敗都不影響其他項。
- **不寫任何資料庫、不寫快取**，純讀。

探測六項：

| # | 目標 | 要回答的問題 |
|---|---|---|
| 1 | `dlFutDataDown` specialid/all 單日 | 主線資料源通不通 |
| 2 | 同上，14 天區間（約 1.8 MB） | 回補那個大回應會不會被切斷／逾時 |
| 3 | `cht/2/stockLists` | 合約乘數對照表 |
| 4 | `cht/5/stockMarginingDown` | 保證金比例 |
| 5 | `cht/5/indexMargingDown` | 微台保證金 |
| 6 | `mis.taifex.com.tw` getQuoteList | **只為 v2 探路**，失敗不影響 v1 |

判讀：1、3、4、5 全過 → 照原設計在雲端跑。
2 失敗 → 回補改成逐日小請求或背景執行緒。
1 失敗 → 整條退回「本機抓→匯入」（`scripts/sync_ssf.py`，比照 `sync_ohlc.py`）。
6 過 → v2 的即時版有戲；失敗 → v2 直接放棄即時，不再花時間。

**這支探測不寫測試**：它會發真實網路請求，樁掉就什麼都沒驗到；它是一次性診斷、驗完刪除，
與正式程式的 TDD 紀律是兩回事（同前兩次 `net-check`／`tv-check` 的處理）。
